# R03: the x402 and B402 payment envelope

Research pass for the BNB Agent Studio marketplace build. Written 2026-09-05. Every claim below is
either labelled verified with the command or URL that proved it or listed as open.

## Headline

The x402 wire format is settled and version 2 is current, but on BSC the only production facilitator
is Binance B402 and its base URL is handed out only with merchant credentials, so the hire flow
should be written to the x402 v2 envelope and demonstrated against a facilitator we run ourselves on
USD1, which is one of only two BSC tokens with native EIP-3009.

## Interfaces and constants

### 1. x402 v2 over HTTP, the whole envelope

Three headers, each carrying base64 of a UTF-8 JSON object. Nothing protocol-relevant lives in the
body.

| Header | Direction | Payload |
| --- | --- | --- |
| `PAYMENT-REQUIRED` | server to client, on the 402 | `PaymentRequired` |
| `PAYMENT-SIGNATURE` | client to server, on the retry | `PaymentPayload` |
| `PAYMENT-RESPONSE` | server to client, on the result | `SettleResponse` |

Facilitators may add `EXTENSION-RESPONSES` on verify and settle responses, base64 JSON keyed by
extension name. It is a sidechannel and is never forwarded to buyers.

Encoding, exactly as the reference implementation does it:

```python
base64.b64encode(model.model_dump_json(by_alias=True, exclude_none=True).encode("utf-8"))
```

Standard base64, camelCase keys, `None` fields omitted. Version detection on the client side reads
`x402Version` from the decoded JSON and defaults to 2 when absent.

`PaymentRequired`, the object inside `PAYMENT-REQUIRED`:

```json
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data",
    "mimeType": "application/json",
    "serviceName": "Example Market Data",
    "tags": ["market-data", "finance"],
    "iconUrl": "https://api.example.com/icon.png"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:84532",
      "amount": "10000",
      "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
      "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USDC", "version": "2" }
    }
  ],
  "extensions": {}
}
```

Field rules for `PaymentRequirements`, the objects inside `accepts`:

| Field | Type | Required | Note |
| --- | --- | --- | --- |
| `scheme` | string | yes | `exact`, `upto`, `batch-settlement`, `auth-capture` |
| `network` | string | yes | CAIP-2, so `eip155:56` for BSC |
| `amount` | string | yes | atomic units, decimal string |
| `asset` | string | yes | token contract or an ISO 4217 code for fiat |
| `payTo` | string | yes | recipient address or a role constant |
| `maxTimeoutSeconds` | number | yes | the buyer's authorization validity budget, not a settlement SLA |
| `extra` | object | optional | reserved protocol keys `assetTransferMethod` and `paymentFlow`, everything else is scheme-specific |

`ResourceInfo` limits, enforced facilitator-side: `serviceName` printable ASCII max 32 chars, `tags`
max 5 entries of max 32 chars each, `iconUrl` max 2048 chars.

`PaymentPayload`, the object inside `PAYMENT-SIGNATURE`, for `exact` on EVM with `eip3009`:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data",
    "mimeType": "application/json"
  },
  "accepted": {
    "scheme": "exact",
    "network": "eip155:84532",
    "amount": "10000",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
    "maxTimeoutSeconds": 60,
    "extra": { "assetTransferMethod": "eip3009", "name": "USDC", "version": "2" }
  },
  "payload": {
    "signature": "0x2d6a7588d6acca505cbf0d9a4a227e0c52c6c34008c8e8986a1283259764173608a2ce6496642e377d6da8dbbf5836e9bd15092f9ecab05ded3d6293af148b571c",
    "authorization": {
      "from": "0x857b06519E91e3A54538791bDbb0E22373e36b66",
      "to": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "value": "10000",
      "validAfter": "1740672089",
      "validBefore": "1740672154",
      "nonce": "0xf3746613c2d920b5fdabc0856f2aeb2d4f88ee6037b8cc5d04a71a4462f13480"

```

The v2 shape moved `scheme` and `network` off the top level into `accepted`, which is a full echo of
the chosen `PaymentRequirements`. `resource` sits at the top level as a `ResourceInfo` object.

`SettleResponse`, the object inside `PAYMENT-RESPONSE`:

```json
{
  "success": true,
  "transaction": "0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef",
  "network": "eip155:84532",
  "payer": "0x857b06519E91e3A54538791bDbb0E22373e36b66",
  "amount": "10000"
}
```

`success`, `transaction` and `network` are required. `transaction` is the empty string when nothing
was broadcast. `errorReason`, `errorMessage`, `payer`, `amount`, `extensions` and `extra` are
optional.

HTTP status mapping: 402 for payment required and for a failed payment, 400 for a malformed payload,
500 for a server error, 200 on success.

### 2. x402 v1 over HTTP, the legacy envelope

Still relevant because B402 keeps a frozen V1 API and because our own prior paywall speaks v1.

The 402 signal is the response **body**, not a header:

```json
{
  "x402Version": 1,
  "error": "X-PAYMENT header is required",
  "accepts": [
    {
      "scheme": "exact",
      "network": "base-sepolia",
      "maxAmountRequired": "10000",
      "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
      "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "resource": "https://api.example.com/premium-data",
      "description": "Access to premium market data",
      "mimeType": "application/json",
      "outputSchema": null,
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USDC", "version": "2" }
    }
  ]
}
```

The buyer replies with `X-PAYMENT`, base64 of:

```json
{
  "x402Version": 1,
  "scheme": "exact",
  "network": "base-sepolia",
  "payload": {
    "signature": "0x...",
    "authorization": { "from": "0x...", "to": "0x...", "value": "10000",
      "validAfter": "1740672089", "validBefore": "1740672154", "nonce": "0x..." }
  }
}
```

The server replies with `X-PAYMENT-RESPONSE`, base64 of the same `SettleResponse` shape. Differences
from v2 that bite: `maxAmountRequired` not `amount`, `resource` is a bare URL string inside each
requirement not a `ResourceInfo` object, network identifiers are names like `base-sepolia` not CAIP-2,
and `scheme` plus `network` sit at the top level of the payload.

### 3. Facilitator interface, request and response shapes

`POST /verify` and `POST /settle` take the same body:

```json
{
  "x402Version": 2,
  "paymentPayload":      { "...": "PaymentPayload" },
  "paymentRequirements": { "...": "PaymentRequirements" }
}
```

`/verify` is read only. It must not write on-chain state or commit payment state. Response:

```json
{ "isValid": true, "payer": "0x857b..." }
{ "isValid": false, "invalidReason": "insufficient_funds", "payer": "0x857b..." }
```

`/settle` commits. Response:

```json
{ "success": true, "payer": "0x857b...", "transaction": "0x1234...", "network": "eip155:84532" }
{ "success": false, "errorReason": "insufficient_funds", "payer": "0x857b...", "transaction": "", "network": "eip155:84532" }
```

`GET /supported`:

```json
{
  "kinds": [ { "x402Version": 2, "scheme": "exact", "network": "eip155:84532" } ],
  "extensions": [],
  "signers": { "eip155:*": ["0x1234..."], "solana:*": ["CKPK..."] }
}
```

`signers` maps a CAIP-2 wildcard namespace to the facilitator's public signer addresses. That is the
EOA whose gas pays for settlement, so it is the address a buyer or a judge can watch on chain.

Payment flow models, declared per asset transfer method through `extra.paymentFlow`:

| Flow | Ordering | Note |
| --- | --- | --- |
| `authorization` (default) | verify, resource, settle, respond | funds move only after the resource succeeds |
| `upfront` | settle, resource, respond | no verify step, settle establishes validity |
| `escrow` | settle, resource, settle, respond | first settle commits a deposit or ceiling |

The invariant: at least one check runs before the resource executes. Clients should prefer
`authorization` when a resource offers both.

### 4. Error codes, complete

Spec-level codes, section 9 of both the v1 and v2 specifications. `invalidReason` carries them on
verify, `errorReason` on settle.

| Code | Meaning |
| --- | --- |
| `insufficient_funds` | payer token balance below the required amount |
| `invalid_exact_evm_payload_authorization_valid_after` | authorization not yet valid |
| `invalid_exact_evm_payload_authorization_valid_before` | authorization expired |
| `invalid_exact_evm_payload_authorization_value_mismatch` | amount does not match (v1 spells it `..._authorization_value`) |
| `invalid_exact_evm_payload_signature` | signature invalid or improperly signed |
| `invalid_exact_evm_payload_recipient_mismatch` | recipient does not match the requirements |
| `invalid_network` | network not supported |
| `invalid_payload` | payload malformed |
| `invalid_payment_requirements` | requirements object invalid |
| `invalid_scheme` | scheme not supported |
| `unsupported_scheme` | scheme not supported by this facilitator |
| `invalid_x402_version` | protocol version not supported |
| `invalid_transaction_state` | on-chain transaction failed or was rejected |
| `unexpected_verify_error` | unmapped verify error |
| `unexpected_settle_error` | unmapped settle error |
| `settlement_pending` | broadcast but confirmation unknown. Non-terminal. Must carry a non-empty `transaction` and `network`. Present in the foundation copy of the v2 spec, absent from the coinbase copy |

`permit2_allowance_required` is the one to handle specially. The EVM exact scheme spec says a
facilitator returns HTTP 412 Precondition Failed with that code when the payer has not approved
Permit2, which tells the client to send a one-time approval and retry.

would allow `unsupported_scheme`. It never emits `settlement_pending`. Envelope checks short-circuit
before payload validation:

| Condition | `invalidReason` |
| --- | --- |
| body missing or unparseable | `invalid_payload` |
| `x402Version` missing or not 2 | `invalid_x402_version` |
| `paymentRequirements.scheme` set and not in `{exact, upto}` | `invalid_scheme` |
| `paymentPayload.accepted.scheme` set and not in `{exact, upto}` | `invalid_scheme` |

### 5. EIP-3009 exactly

Interface, verbatim parameter order from the ERC. Order is load bearing, the digest depends on it.

```solidity
event AuthorizationUsed(address indexed authorizer, bytes32 indexed nonce);
event AuthorizationCanceled(address indexed authorizer, bytes32 indexed nonce); // optional
```

The domain. Four-field EIP-712 domain, typehash

Signature split from the 65-byte hex string: `r = sig[0:66]`, `s = "0x" + sig[66:130]`,
`v = "0x" + sig[130:132]`. When `v` comes back as 0 or 1, add 27.

Nonce is a random 32-byte value, not a counter. That is the whole point of ERC-3009 over ERC-2612: a
payer can have many authorizations outstanding at once with no ordering constraint. Replay is stopped
by the contract marking `_authorizationStates[from][nonce] = true` and emitting `AuthorizationUsed`.

Contract-side ordering of checks, from the reference implementation, which is also the order our own
facilitator should mirror when deciding which error to return:

1. `now > validAfter`, else `EIP3009: authorization is not yet valid`
2. `now < validBefore`, else `EIP3009: authorization is expired`
3. `!_authorizationStates[from][nonce]`, else `EIP3009: authorization is used`
4. `ecrecover(digest, v, r, s) == from`, else `EIP3009: invalid signature`. A zero recovered address
   must be rejected, since malformed signatures recover to zero
5. mark the nonce, emit `AuthorizationUsed`, transfer

`cancelAuthorization` is the escape hatch. The payer signs
`CancelAuthorization(address authorizer, bytes32 nonce)` over the same domain, anyone submits it, the
nonce is burned and `AuthorizationCanceled` fires. It is optional in the ERC. On BSC, USD1 exposes
`CANCEL_AUTHORIZATION_TYPEHASH()` with the canonical value, so the path exists there.

`receiveWithAuthorization` differs from `transferWithAuthorization` in exactly one way: it also
requires `msg.sender == to`. The ERC's security section says to use it whenever the call comes from
another contract, because an observer can otherwise lift the authorization out of the mempool and
front-run the wrapper, executing the bare transfer and leaving the wrapper's bookkeeping unrun. For a
facilitator that is an EOA paying gas and transferring straight to the seller, `transferWithAuthorization`
is correct. For any design where a contract of ours receives the funds and then does something (a
marketplace escrow, a fee split), `receiveWithAuthorization` is the only safe choice. I verified USD1
implements it and enforces the guard.

Payload shape on the wire. Note `permit2Authorization` replaces `authorization`. The two must
never both be present:

```json
"payload": {
  "signature": "0x<65 bytes>",
  "permit2Authorization": {
    "permitted": { "token": "0x55d398326f99059ff775485246999027b3197955", "amount": "5000000" },
    "from": "0x<payer>",
    "spender": "0x<extra.spenderAddress, the proxy, not the facilitator EOA>",
    "nonce": "<uint256 as decimal string, random>",
    "deadline": "<unix seconds as decimal string>",
    "witness": { "to": "0x<payTo>", "validAfter": "<unix seconds as decimal string>" }
  }
}
```

For `permit2-upto` the witness gains `"facilitator": "0x<extra.signerAddress>"` between `to` and
`validAfter`.

Every numeric field travels as a decimal string on the wire and signs as `uint256`. `nonce` is a
256-bit random value, not a counter, because Permit2 tracks it as a bitmap.

Two prerequisites that verify does not catch and that will bite in a demo:

1. The payer must have run `token.approve(0x000000000022D473030F116dDEE9F6B43aC78BA3, 2^256-1)` once
   per token, paying its own gas in BNB. Without it, settlement reverts on chain with
   `TRANSFER_FROM_FAILED`. A finite approval works once then breaks, because each transfer consumes it.
2. `witness.validAfter` must be at or below the settling block's timestamp. Back-date by about 60 s to
   absorb clock skew. `"0"` is also valid. Replay protection comes from the nonce, not from `validAfter`.

So the Permit2 path is not gasless for the buyer's first payment in a given token. Only the EIP-3009
path is truly gasless from the first call.

Decimals are the single most expensive trap here. Binance shipped it wrong once. Their changelog
for 2026-05-19 records that all four mainnet tokens were documented as 6 decimals when the chain says
18. It also records that merchants pricing at `amount: "10000"` for one cent were charging 1e-14 of a token. At 18
decimals, one cent is `10000000000000000`. My own reads confirm 18 on all four mainnet tokens. They also confirm testnet is mixed: 6, 6 and 18. So decimals must be read per token per environment.

Signature scheme. There are two independent signatures in a B402 flow. Conflating them is a
common mistake:

1. The **buyer's** EIP-712 secp256k1 signature over `TransferWithAuthorization` or
   `PermitWitnessTransferFrom`. This is the payment authorization.
2. The **merchant's** RSA-SHA256 signature over `jsonBody + timestampMillis`, sent in `X-Tesla-Signature`.
   This authenticates the merchant to the Binance gateway and has nothing to do with the payment.

The merchant signing recipe, exactly:

```python
body = "{}"                                   # the exact serialized bytes you will send
timestamp = str(int(time.time() * 1000))      # milliseconds, not seconds
to_sign = (body + timestamp).encode("utf-8")
priv = RSA.import_key(base64.b64decode(PRIV_KEY_B64))   # 1024-bit, PKCS#8 DER, base64, no PEM header
signature = base64.b64encode(pkcs1_15.new(priv).sign(SHA256.new(to_sign))).decode()

headers = {
  "Content-Type": "application/json",
  "X-Tesla-ClientId": CLIENT_ID,
  "X-Tesla-SignAccessToken": ACCESS_TOKEN,
  "X-Tesla-Timestamp": timestamp,     # must equal the value concatenated above
  "X-Tesla-Signature": signature,
}
```

Serialize once and reuse the same string for both the body and the signing input. Re-serializing with
different key ordering or whitespace produces a different signature.

Hosted facilitator and access:

- Authenticated surface `/papi/v2/b402/{supported,verify,settle}`. Base URL is not published for
  either environment and ships with the credentials.
- Public discovery surface, no auth, published and hardcodable:
  `https://www.binance.com/bapi/ramp/v1/public/ramp/b402`.
- Onboarding is a Google Form, separately per environment. Sandbox and production do not share
  credentials, keys or IP whitelists. You submit a business name, contact email, an EVM wallet address
  to receive funds, your RSA public key, your source IPs and an optional webhook URL. You get back a
  clientId, an accessToken and a public key for webhook verification.
- Yes there is a testnet. The docs say B402 is live on testnet for external partners with mainnet
  granted on request.

B402's declared deviations from the x402 v2 spec, all of them deliberate:

| Deviation | Detail |
| --- | --- |
| `POST /supported` | The spec says GET. The Binance gateway signs every request body, so a body-less GET would break the auth model. Send `{}` |
| `"upto"` scheme | Not in the spec. Buyer authorizes a cap, merchant charges at most that cap |
| `assetTransferMethod` values `permit2-exact` and `permit2-upto` | The spec's EVM binding names the method `permit2`. B402 splits it in two |
| `settleAmount` on the settle body | Required for `permit2-upto`, ignored otherwise. Keeps `paymentRequirements` immutable across verify and settle rather than mutating `amount` as the spec suggests |
| `extra.signerAddress` and `extra.spenderAddress` | Occupy the spec-reserved `extra` slot. They replace V1's overloaded `extra.facilitatorAddress` |

Scheme mapping, which is where a naive integration breaks. B402 puts the transfer method in
`extra.assetTransferMethod` and keeps `scheme` at the spec value, except that `permit2-upto` moves the
scheme to `upto`:

| `assetTransferMethod` | `scheme` | `payload` key | extra witness field |
| --- | --- | --- | --- |
| `eip3009` | `exact` | `authorization` | none. `spenderAddress` is absent |
| `permit2-exact` | `exact` | `permit2Authorization` | none |
| `permit2-upto` | `upto` | `permit2Authorization` | `witness.facilitator` must equal `extra.signerAddress` |

The merchant's hard obligation. B402 requires the merchant to copy the whole `kinds[].extra` object
from its cached `/supported` response into the 402 it returns to the buyer: `name`, `version`,
`assetTransferMethod`, `signerAddress` and, for permit2, `spenderAddress`. Buyers cannot call
`/supported`, so the 402 is their only channel. Omitting any of it produces signatures B402 rejects
with `invalid_payload`. The docs say do not hardcode these, because the Permit2 proxies can be
redeployed.

Settlement outcomes, plus the one thing an integrator must get right:

| Outcome | `success` | `transaction` | `errorReason` | Action |
| --- | --- | --- | --- | --- |
| Settled, terminal | `true` | hash | absent | done |
| Failed, terminal | `false` | `""` empty | present | done, read the reason |
| Broadcast, unresolved | `false` | non-empty hash | absent or `invalid_transaction_state` | keep polling `/settle` |

`transaction` is the discriminator, not `errorReason`. A confirmed on-chain revert and a pending
confirmation both surface as `success: false` plus a hash plus `invalid_transaction_state`. Poll
`/settle` at 3 to 5 s, well past `maxTimeoutSeconds`, because the backend reconciles a broadcast
transaction for up to about 30 minutes. `/settle` is idempotent on `(nonce, network, payer)` so
polling does not double charge. Never key success on the HTTP status, which is always 200.

Published latency estimates: about 10 s for small amounts, 25 s medium, 45 s large. The synchronous
window inside `/settle` is about 20 s.

Listing is opt-in and rides on settlement. A merchant attaches `extensions.bazaar` to the
`paymentPayload` on every V2 settle:

```json
"extensions": {
  "bazaar": {
    "info": {
      "input":  { "type": "http", "method": "GET", "queryParams": { "symbol": "BTC" },
                  "headers": { "X-Client-Version": "1" } },
      "output": { "type": "json", "example": { "symbol": "BTC", "price": 67000, "ts": 1700000000 } }
    },
    "schema": { "$schema": "https://json-schema.org/draft/2020-12/schema", "type": "object",

    "routeTemplate": "/users/:userId",

  }

```

`info` and `schema` are required, `routeTemplate` and `description` optional. Three `info.input`
variants: HTTP query methods (`GET`, `HEAD`, `DELETE`), HTTP body methods (`POST`, `PUT`, `PATCH`, which
add `bodyType` and `body`) and MCP tools (`type: "mcp"` with `tool`, `inputSchema` and `example`). For
MCP the listing key is `(resource.url, info.input.tool)`, otherwise it is `(payTo, resourceUrl)`.
Multi-chain listings merge on `(scheme, network, asset)` with last settle winning. Listing without
settling is not possible.

Ranking blends text relevance, recent activity with a 30-day decay, unique-payer diversity and fail
rate. Resources with a 24-hour fail rate over 50% are filtered out entirely. A settle below about one
US cent does not count toward the activity signal.

| 6 decimals everywhere, `price_atomic / 1_000_000`, `DEFAULT_PRICE_ATOMIC = 10000` | BSC mainnet stablecoins are 18 decimals, so this underpays by 1e12 | 18 decimals on mainnet. Read `decimals()` per token because testnet mixes 6 and 18 |
| `x402Version: 1` with top-level `scheme` and `network`, `maxAmountRequired`, `X-PAYMENT` header | v1 shape. B402 V2 rejects anything but `x402Version: 2` with `invalid_x402_version` | v2 shape with `accepted`, `amount`, `PAYMENT-SIGNATURE` |
| Hardcoded `nativeCurrency` of USDC with 6 decimals in the add-chain call | BSC's native currency is BNB with 18 decimals | `{ name: "BNB", symbol: "BNB", decimals: 18 }` |
| Assuming `transferWithAuthorization` alone suffices | USDT and USDC on BSC have no EIP-3009 at all | add the Permit2 path or restrict pricing to U and USD1 |

The `x402` python package installed here is version 2.13.0 from the x402 Foundation, so it already
speaks v2. `facilitator.py` builds against `x402.schemas` classes that exist in both shapes
(`PaymentPayload` and `PaymentPayloadV1`), so the port is a config change plus a switch to the v2
classes, not a rewrite.

## Design implications for the marketplace

1. **Build to x402 v2, not v1.** B402's V2 endpoint rejects any other version outright. Version 2 is also the current spec. Emit `PAYMENT-REQUIRED` on the 402, accept `PAYMENT-SIGNATURE` on the retry, return
   `PAYMENT-RESPONSE`. Where a B402 doc line asks for `X-PAYMENT-REQUIREMENTS` instead, send both: the
   header costs nothing and B402 never reads the buyer-facing 402 anyway, only the merchant's own
   `/verify` body.

2. **Do not block the build on B402 credentials.** The base URL is not published, onboarding is a manual
   per-environment form. The deadline is 2026-09-09. Write the resource server against a
   `FacilitatorClient` interface with two implementations: an in-process facilitator we control plus a
   B402 HTTP client. The in-process one is what the demo runs on. If credentials arrive, the B402 client
   is a config flip. This is exactly the shape our prior paywall already had.

3. **A self-hosted facilitator on BSC works today with the official SDK.** BSC is absent from both
   SDKs' network tables, but the python SDK's `get_network_config` falls back to `{"chain_id": n}` for
   any `eip155:*`. The exact-EVM facilitator reads the EIP-712 domain from `requirements.extra`
   rather than a registered asset. So `register_exact_evm_facilitator(f, signer, networks="eip155:56")`
   plus correct `extra.name` and `extra.version` is enough. Nothing needs patching.

4. **Price in USD1 for the demo.** It is the only BSC token where all of the following hold: native
   EIP-3009 verified on chain, the canonical typehashes exposed and matching, ERC-5267 `eip712Domain()`
   available so the domain can be read programmatically rather than guessed, plus the Bazaar's own
   traffic already concentrated there (97 of the first 100 listings). Truly gasless for the buyer, first
   call included.

5. **Never hardcode `extra.name`. Read it.** The U token's ERC-20 `name()` is "United Stables" while
   Binance's docs example shows `extra.name: "U"`. On testnet the same brand really is "U". Get it
   from ERC-5267 `eip712Domain()` when present, otherwise brute-force the domain separator against
   candidate name and version pairs at startup and fail loudly on no match. A one-off startup check
   costs two RPC calls and removes the entire class of `invalid_exact_evm_payload_signature` failures.

6. **Read `decimals()` per token per environment and store atomic amounts as strings.** BSC mainnet is
   18 across all four tokens, testnet is 6, 6 and 18. Binance shipped this wrong in their own docs for
   about a month. One cent of USD1 is `10000000000000000`. Never reuse a 6-decimal constant.

7. **Offer both transfer methods or accept a narrow token list.** If the marketplace prices in USDT or
   USDC (the tokens most agents actually hold on BSC) then Permit2 is mandatory. The buyer's first
   payment in each token needs a one-time `approve(Permit2, max)` that costs the buyer BNB gas. Surface
   that as an explicit onboarding step in the UI, detect a missing allowance before signing. Do not
   advertise the flow as gasless for that path.

8. **Treat settlement as asynchronous from day one.** Poll `/settle`, key the outcome on `transaction`
   being empty or not, then hold the resource until `success: true`. A single `success: false` read as
   terminal will book paid calls as failures. Enforce our own idempotency on `(nonce, network, payer)`
   as well as relying on the facilitator's.

9. **Use `receiveWithAuthorization` if any contract of ours ever holds the funds.** For a plain
   facilitator-to-seller transfer, `transferWithAuthorization` is right. The moment we introduce an
   escrow, a fee split or a marketplace vault, the ERC's front-running warning applies and only the
   `receiveWithAuthorization` payee guard closes it. USD1 implements the guard, verified.

10. **The `upto` scheme is the right primitive for metered agent work.** A rebalancing or yield agent
    cannot know its cost before it runs. `upto` lets the buyer authorize a ceiling once then be charged
    the true amount at settle via `settleAmount`. It is a B402 extension, not core spec. The
    canonical `x402UptoPermit2Proxy` is already deployed on BSC, so the primitive exists either way.

11. **Read the Bazaar, do not duplicate it.** 979 live BSC resources, public and unauthenticated, with
    per-resource call counts and unique-payer counts. Ingesting it gives the marketplace a real
    populated catalog on day one and gives the Data Quality criterion something measurable to point at.
    Budget for a normalizing adapter, because the live shape uses `scheme` for the transfer method and
    `maxAmountRequired` for the amount.

12. **Listing our own agents in the Bazaar rides on settlement.** Attach `extensions.bazaar` to every V2
    settle and the endpoint becomes agent-discoverable with no separate registration. That requires B402
    credentials, so it is a stretch goal, not a dependency. Note it also requires a real settle to have
    happened, which is a reason to get testnet credentials early even if mainnet does not land.

13. **Pin the spec copy we cite.** Two live copies of the v2 specification differ. Binance links the
    smaller coinbase one. Cite `x402-foundation/x402` with today's date and keep the raw capture, so a
    judge or a maintainer can see which text we built against.

14. **Watch the name collision.** An unrelated project also calls itself b402 (`docs.b402.ai`, npm and
    GitHub packages). Any dependency we pull must come from Binance's documented surface or from the
    x402 Foundation packages, never from a package that merely matches the name.

## Integration decision table: charging for one agent call on BSC

Path A, recommended for the demo. `exact` with `eip3009`, USD1 on `eip155:56`, our own facilitator.

| Step | Actor | Exactly what happens |
| --- | --- | --- |
| 1 | Buyer agent | `GET /agents/{id}/invoke`. No payment attached |
| 2 | Marketplace resource server | Replies `402` with `PAYMENT-REQUIRED` set to base64 of `{"x402Version":2,"error":"PAYMENT-SIGNATURE header is required","resource":{...},"accepts":[{"scheme":"exact","network":"eip155:56","amount":"10000000000000000","asset":"0x8d0D000Ee44948FC98c9B98A4FA4921476f08B0d","payTo":"0x<seller>","maxTimeoutSeconds":300,"extra":{"assetTransferMethod":"eip3009","name":"World Liberty Financial USD","version":"1"}}]}` |
| 3 | Buyer agent | Signs, sends no transaction. The bytes signed are `keccak256(0x19 ‖ 0x01 ‖ D ‖ S)` where `D = keccak256(abi.encode(0x8b73c3c6...400f, keccak256("World Liberty Financial USD"), keccak256("1"), 56, 0x8d0D000Ee44948FC98c9B98A4FA4921476f08B0d))` and `S = keccak256(abi.encode(0x7c7c6cdb...2267, from, to, value, validAfter, validBefore, nonce))`. Produces 65 bytes `r ‖ s ‖ v` |
| 4 | Buyer agent | Retries the request with `PAYMENT-SIGNATURE` set to base64 of the v2 `PaymentPayload` carrying `payload.signature` plus `payload.authorization` |
| 5 | Marketplace resource server | Calls facilitator `verify`. Read only, no transaction, no gas |
| 6 | Marketplace resource server | Runs the agent call and produces the result |
| 7 | Facilitator (our relayer EOA) | Submits **one** transaction: `to = 0x8d0D000Ee44948FC98c9B98A4FA4921476f08B0d`, `data = 0xe3ee160e ‖ abi.encode(from, to, value, validAfter, validBefore, nonce, v, r, s)`, `value = 0`. The v,r,s overload, because USD1 does not expose the `bytes` overload |
| 8 | Facilitator | **Pays the gas, in BNB, from the relayer EOA.** This is the only account that needs BNB. Buyer needs none, seller needs none |
| 9 | Marketplace resource server | Returns 200 with `PAYMENT-RESPONSE` set to base64 of the `SettleResponse` carrying the transaction hash |

Path B, if the price is in USDT or USDC. `exact` with Permit2.

| Step | Actor | Exactly what happens |
| --- | --- | --- |
| 0, once per token per wallet | Buyer | Submits `token.approve(0x000000000022D473030F116dDEE9F6B43aC78BA3, 2^256-1)` and **pays its own BNB gas**. Skipping this makes settlement revert with `TRANSFER_FROM_FAILED` |
| 1 to 2 | as Path A | `extra` additionally carries `assetTransferMethod: "permit2-exact"` and `spenderAddress` |
| 3 | Buyer | Signs `PermitWitnessTransferFrom` over the three-field Permit2 domain `{name:"Permit2", chainId:56, verifyingContract:0x0000...78BA3}`, with `spender` set to the proxy and `witness = {to: payTo, validAfter}`. Sends no transaction |
| 7 | Facilitator | Submits one transaction to the proxy `settle(permit, owner, witness, signature)`, which calls `Permit2.permitWitnessTransferFrom` and moves tokens straight to `witness.to` |
| 8 | Facilitator | Pays the gas in BNB. The buyer already paid gas once, at step 0 |

Path C, if B402 credentials land. Same buyer bytes as Path A or B. The difference is only who runs steps
5 and 7.

| Step | Actor | Exactly what happens |
| --- | --- | --- |
| 5 | Marketplace server | `POST {BASE_URL}/papi/v2/b402/verify` with `{x402Version:2, paymentPayload, paymentRequirements}`, RSA-signed, from a whitelisted IP. HTTP 200 with `data.isValid` |
| 7 | Marketplace server | `POST {BASE_URL}/papi/v2/b402/settle`, same body plus `settleAmount` when the method is `permit2-upto`. B402's signer EOA submits the on-chain transaction |
| 8 | B402 | **B402 pays the gas.** No BNB anywhere in our stack. We must still poll `/settle` until `success: true` or a `transaction: ""` terminal failure |

Who signs what, in one line each. The buyer signs an EIP-712 typed-data digest over the token's own
domain (EIP-3009) or over the Permit2 domain. It never sends a transaction. The facilitator signs and
broadcasts exactly one Ethereum transaction and pays its gas in BNB. The seller signs nothing on chain
and receives tokens directly. Under Path C the merchant additionally signs each API request with RSA,
which authenticates the merchant and moves no money.
