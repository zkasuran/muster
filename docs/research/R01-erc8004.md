# R01: the ERC-8004 surface on BSC, to the byte

Research pass run 2026-09-05 against BSC mainnet (chain id 56) with cast 1.7.1, node 22 and curl.
Every signature below was proven at its live address, not read out of the spec. Views were called.
Writes were simulated with `eth_call --from` and produce the exact revert strings the source
defines, which proves the selector is routed and the guard is real. Events were matched against
real logs pulled with `eth_getLogs`.

## Headline

The Validation Registry **is** deployed and fully functional on BSC at
`0x8004Cc8439f36fd5F9F049D9fF86523Df6dAAB58` (8004scan simply does not list it). It is
completely unused: zero validation requests across 1,999 sampled agentIds. Enumeration needs no
log scanning at all, because agentIds are contiguous `0 .. _lastId-1` and `_lastId` is a single
`eth_getStorageAt` at slot `0xa040f782729de4970518741823ec1276cbcd41a0c7493f62d173341566a04e00`
(334,924 at block 120,025,025). A full sweep of every agent's `tokenURI`, `ownerOf` and
`getAgentWallet` takes about 30 minutes and 670 `eth_call`s through Multicall3 on a free RPC.

## Unverified or open

| claim | blocker |
| --- | --- |
| The block each proxy was created at | The registry proxies emit no `Upgraded` log in blocks 79,080,000 to 79,094,900, so creation is earlier than the first registration. No free BSC RPC I found serves historical `eth_getCode`: publicnode refuses archive without a token, blxrbdn answers `not supported`, zan.top answers `state … is not available` for most old blocks. The first registration block 79,094,807 is verified and is the only block number a builder actually needs. |
| Total feedback count on BSC | 8004scan's 11,719 figure (2026-08-27 capture) cannot be reproduced from a full log scan, because no free RPC gives both archive depth and a range over 10,000 blocks. My 388 figure is from a 2,098-agent sample and is a lower bound on the sample, not a chain total. |
| Whether `FeedbackRevoked` and `ResponseAppended` have ever fired on BSC | Zero revoked entries in 388 surveyed feedbacks and zero replies in the 8004scan feedback list for chain 56. Both functions are proven callable by simulation, but I could not point at a real log. |
| `agentWallet` being cleared on transfer | Read from source (`_update` writes `""` and emits `MetadataSet(id,"agentWallet","agentWallet","")`) and consistent with the 1 empty value in 136 sampled ids. No transfer happened inside the 4,500-block window I scanned, so I have no observed log of the clearing. |
| That the deployed implementations are byte-identical to the repo source | The repo has no verified-source link and BscScan needs an API key. Match is inferred from an exact dispatch-table match, the ERC-7201 slot constants matching the source comments, `getVersion()` returning `"2.0.0"` and every revert string matching. Strong, not proof. |
| Whether the Safe or the EOA has ever exercised the upgrade path | Would need the proxies' full `Upgraded` log history, blocked by the same archive limit. |


It `SLOAD`s the EIP-1967 implementation slot and `DELEGATECALL`s. There is no admin slot, no
beacon, no ifAdmin branch. Upgrade authority therefore lives in the implementation
(`_authorizeUpgrade` is `onlyOwner`), reached through `upgradeToAndCall(address,bytes)`.

### setAgentWallet: the exact EIP-712 payload

```
domain = {
  name: "ERC8004IdentityRegistry",
  version: "1",
  chainId: 56,
  verifyingContract: "0x8004A169FB4a3325136EB29fA0ceB6D2e539a432"
}
// eip712Domain() returns fields=0x0f, salt=0x0, extensions=[]  (verified live)

AgentWalletSet(uint256 agentId,address newWallet,address owner,uint256 deadline)
// typehash = cast keccak "AgentWalletSet(uint256 agentId,address newWallet,address owner,uint256 deadline)"
```

The signature must come from `newWallet`, not from the agent owner: `ECDSA.tryRecover(digest,sig)`
must recover `newWallet`, else the contract falls back to
`IERC1271(newWallet).isValidSignature(digest,sig) == 0x1626ba7e`. `owner` inside the struct is
`ownerOf(agentId)` as read on chain, not `msg.sender`.

**`deadline` must satisfy `block.timestamp <= deadline <= block.timestamp + 300`.** A five minute
window, enforced on both sides, so a signature cannot be prepared far ahead. That is the single
most common way this call fails.

Two asymmetries a builder will trip over. **`getSummary` rejects an empty `clientAddresses` array**
and reverts `clientAddresses required`, but **`readAllFeedback` with an empty array falls back to
every client that ever rated the agent**. So the only client-list-free on-chain read path is
`readAllFeedback`. Any aggregate score has to be computed off it. `getClients(agentId)` gives
the list if you want `getSummary`.

`feedbackIndex` is 1-indexed per `(agentId, clientAddress)` pair, not global. Index 0 always reverts.

### The getSummary aggregation formula, exactly

Read from the deployed contract's source, matching the verified dispatch table:

```
for each client in clientAddresses:
  for j in 1..getLastIndex(agentId, client):
    skip if isRevoked
    skip if tag1 != "" and keccak(tag1) != keccak(fb.tag1)
    skip if tag2 != "" and keccak(tag2) != keccak(fb.tag2)
    sum += fb.value * 10**(18 - fb.valueDecimals)     // normalise to WAD
    decimalCounts[fb.valueDecimals]++
    count++
modeDecimals   = argmax(decimalCounts)                 // lowest d wins a tie
summaryValue   = (sum / count) / 10**(18 - modeDecimals)
summaryDecimals = modeDecimals
```

The average is taken in 18-decimal fixed point then truncated down to the **modal** decimals of the
inputs. Mixing a `valueDecimals=0` score of 87 with a `valueDecimals=2` score of 9977 gives an
answer in whichever decimals occurred more often, so a caller has to read `summaryValueDecimals` and
rescale. `value` is bounded to +/-1e38 on write, `valueDecimals` to 0..18.

## Enumeration: the working recipe

There is no `totalSupply`, but there is no need for a log scan either, because `register()` does
`agentId = $._lastId++` and there is no burn function in the ABI. agentIds are contiguous from 0.

**Step 1, exact count, one call, zero cost:**

```bash
cast storage 0x8004A169FB4a3325136EB29fA0ceB6D2e539a432 \
  0xa040f782729de4970518741823ec1276cbcd41a0c7493f62d173341566a04e00 \
  --rpc-url https://bsc-rpc.publicnode.com | xargs cast to-dec
# 334924   at block 120025025, 2026-09-05  =>  agentIds 0 .. 334923
```

Cross-checked two ways: a binary search on `ownerOf` found the highest owned id. A simulated
`register()` returned the next id to be minted.

**Step 2, sweep every agent through Multicall3.** `aggregate3((address,bool,bytes)[])` is
`0x82ad56cb`. 500 agents times three reads (`tokenURI` `0xc87b56dd`, `ownerOf` `0x6352211e`,
`getAgentWallet` `0x00339509`) is 1,500 sub-calls and fits one `eth_call`. Measured on
`https://bsc-rpc.publicnode.com`:

| sub-calls per eth_call | response | latency |
| --- | --- | --- |
| 50 | 11.5 KB | 0.73 s |
| 400 | 94 KB | 1.33 s |
| 800 | 357 KB | 1.70 s |
| 1500 | 621 KB | 1.39 s |
| 2500 | fails | `execution aborted (timeout = 30s)` |

Ten consecutive batches of 500 agents (15,000 sub-calls) with a 250 ms gap: **27.3 s wall, zero
failures, 183 agents/s**. Extrapolated to the whole registry: **about 30.5 minutes, 670 `eth_call`s,

## On-chain metadata keys: what is reserved, what is really populated

## Design implications for the marketplace

**1. Index from storage plus Multicall3, not from a log scan.** One `eth_getStorageAt` gives the exact
agent count, ids are contiguous from 0, then 670 `eth_call`s sweep every agent's URI, owner and wallet
in half an hour on a free RPC. Build the catalogue that way and keep it fresh with a delta on
`_lastId`. Reserve `eth_getLogs` for the three `NewFeedback` fields that exist only in events. This
also means the marketplace does not depend on 8004scan's index, which is currently `status: down` for
BSC with its newest indexed feedback five days stale at block 119,137,534 against head 120,025,025.

**2. Treat `tokenURI` as hostile input.** Six parsers are needed, not one: base64 data URI, **gzip
data URI** (`enc=gzip;level=6`), `https`, `ipfs`, empty, then raw-JSON-without-a-prefix. About 5% of
agents hold something no parser can use. About 5% of off-chain URIs 404 or return HTML. Every
agent card in the UI needs a defined state for "registration file unreadable". A judge scoring
Data Quality will look for exactly that. Showing 334,924 agents with 5% broken cards scores worse
than showing a filtered, labelled catalogue with the reject count on screen.

**3. Read both spellings of the two flags that have two spellings.** `x402Support` and `x402support`,
`supportedTrust` and `supportedTrusts`. Each misspelling is on about 5% of documents, so ignoring
them silently mislabels roughly one agent in twenty on the two fields the sponsors care about most.

**4. There is no category field, so the four mandated categories must be derived.** The only
category-shaped data on chain is TermiX's `termix.profile.category` (which reads `"general"` on the
samples I pulled), `termix.tags`, `roles`, `attributes[].trait_type == "tag"`, plus OASF skill paths
inside `services[].skills`. `getMetadata(id,"category")` is populated on zero agents. So classification
into rebalancing, grid trading, yield and health factor is our own inference layer over name,
description, tags and OASF skills. It should be visible and auditable in the product, because the
rubric names Agent Diversity as one of three criteria. Publishing the classifier's rule set and its
per-category counts is cheap evidence for that criterion.

**5. Reputation must be surfaced honestly or it will hurt us.** 388 entries across 299 of 2,098
sampled agents, 68% of them from one spam address, every value at `valueDecimals = 0`, zero
revocations. A five-star average computed naively puts a Telegram advertiser's "100" on top. Filter by
client, which is what `getSummary(agentId, clientAddresses, tag1, tag2)` is for, then show the client
count next to any score. `readAllFeedback(id, [], "", "", false)` is the only client-list-free on-chain
read, so use that to build the client list then aggregate off it.

**6. The Validation Registry is an open goal.** It is deployed on BSC, correctly wired to the Identity
Registry, callable (a `validationRequest` from an agent owner simulates clean), with zero usage
anywhere 8004scan indexes. Writing one real request plus one real validator response on BSC mainnet
gives the submission an on-chain artifact nobody else has. It lines up with the TermiX rubric's
"proven agent advantage" and "high-stakes categories" weightings. The catch is that no third-party
validator exists, so we register the validator address ourselves and say so plainly. `requestHash` is
caller-chosen and must be unique, `response` is 0..100, `validationResponse` can be called repeatedly
on the same hash with different `tag` values for progressive finality.

**7. Record the upgrade risk, because it is real.** Both the Identity and Reputation registries can be
replaced at will by a 3-of-5 Safe at `0xF223968Dd0c66472E31043acAcCcF5D1464D644b`. The Validation
Registry can be replaced by a **single EOA** at `0x8888d0A88ef8302dfa4BA53c41c2fE3c4E486f42`. An upgrade could change
the storage meaning of every agent record the marketplace shows. Pin the implementation addresses seen
at build time (`0x7274e874CA62410a93Bd8bf61c69d8045E399c02`,
`0x16e0FA7f7C56B9a767E34B192B51f921BE31dA34`, `0xDB31f5d9167f8ebc8B30FbBF814c4d297c2D7F99`), read the
EIP-1967 slot on each sync, then surface a banner when it moves. That is one storage read per sweep and
it turns an unmanaged dependency into a monitored one.

**8. `setAgentWallet` is the payment hook. Its deadline is five minutes.** If the marketplace
offers agents a verified receiving wallet for x402 or B402 settlement, the signing flow has to build
the EIP-712 digest, get it signed by the **new wallet** (not the owner) and land the transaction inside
300 seconds. Otherwise it reverts `deadline too far` or `expired`. Nobody on BSC has done this yet:
all 541 non-zero `agentWallet` values in my sample still equal `ownerOf`. Getting it working is a
demonstrable first.

**9. Operator delegation is free and useful.** Every mutating identity call accepts
`isApprovedForAll(owner, msg.sender)`, so a user can `setApprovalForAll(marketplace, true)` once and
the marketplace can then manage URIs, metadata and wallets for their whole fleet without custody of
the tokens. That is a clean product story with no new contract.

**10. Everything cross-chain is free.** The same three addresses exist on 23 mainnets and 25 testnets
from one CREATE2 factory, with `getIdentityRegistry()` on BSC returning the BSC identity address, so an
`eip155:<chainId>:0x8004A169…` key generalises with no per-chain configuration beyond an RPC URL.
(Corrected 2026-09-05: this line first said 24 mainnets. `MAINNET_CHAIN_IDS` in
`raw/erc8004-scripts-addresses-2026-09-05.ts` holds 23 entries and `TESTNET_CHAIN_IDS` holds 25. Counted
from the capture, then the raw URL was re-fetched and came back byte-identical to it at 5,935 bytes.
Neither list contains 204 or 5611.)
BSC is the biggest registry by agent count: 334,924 read live from `_lastId` today, against the
2026-08-27 8004scan capture that put BSC at 287,029 with Base second at 52,588. That is the argument
for BSC being where the marketplace belongs. It also means the marketplace can offer a
cross-chain view for free once the BSC path works.
